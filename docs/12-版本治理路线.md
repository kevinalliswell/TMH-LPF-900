# 12 版本治理与长期路线

本文把“代码能构建”提升为“可追溯、可复现、可现场验收的产品版本”。安全相关修复优先于功能扩展。

## 12.1 版本与 Tag 规则

- 严格使用 SemVer：不兼容的数据/协议变化升 `MAJOR`，向后兼容功能升 `MINOR`，修复升 `PATCH`。
- `package.json.version` 是版本单一来源；`pnpm sync-version` 同步 Cargo workspace、Tauri 配置与 UI。
- 当前 `[Unreleased]` 软件安全基线（含认证/RBAC 与授权回归）目标版本为 `v0.2.1`；真实传输、端口探针和现场硬件联调仍属于 `v0.3.x`。目标版本不是已发布版本。
- 不补打 `v0.1.0`：它只有 CHANGELOG 历史记录，没有形成经过当前门禁验证的可发布基线。
- 仓库已有2026-08-31发布的`v0.2.0`，tag提交为`cbed665`，早于当前main和本轮门禁。本轮开发源码仍显示0.2.0，不能据此覆盖历史tag或混用产物；下一次发版PR必须确定新的未使用版本，再从受保护main创建新tag。
- `v0.2.1` 仅作为本轮未发布修复的计划目标；依照 §12.2，只有独立发版 PR 才更新版本同步点并生成新包/标签。本轮 PR 不改 `package.json`、Cargo 或 Tauri 版本。
- 禁止移动、覆盖或删除已发布 tag。发布失败用新 patch/prerelease 版本修复，不改写历史。

## 12.2 发版 PR 门禁

发版 PR 必须同时完成：

1. 把 `[Unreleased]` 归档为带日期的版本节，并创建新的空 `[Unreleased]`；
2. 更新 `package.json.version`，运行 `pnpm sync-version` 与全量 CI；
3. 附上硬件/安装验收记录或明确标记未完成项；
4. 至少一名维护者批准，所有 required checks 通过后合并；
5. 在合并后的 `main` 顶端创建 `v<version>` tag。

Release 工作流只响应 tag，并拒绝下列输入：非 SemVer tag、版本点不一致、CHANGELOG 无对应章节、
tag 不在当前 `main` 顶端、使用 lightweight tag、main 未开启保护，或该提交未通过 main push CI。工作流只产出草稿 Release；签名、安装与更新链路复核后再人工发布。

## 12.3 GitHub 分支保护实况

2026-10-27 已为 `main` 启用并通过 GitHub API 回读验证：必须经 PR、分支保持最新、至少一名 reviewer 批准且新提交会废弃旧批准；Ubuntu/Windows CI 与 `RustSec CI / audit` 为 required checks；管理员也受规则约束；禁止 force push、删除及未解决会话。当前 `main` push CI 成功记录为 run `34762466553`。

直接协作者目前只有仓库所有者。当前 PR 由所有者发起，因此需要增加一名可审阅的维护者后才能合并；不降低审批要求来绕过该限制。该任务不合并任何 PR。`v*` tag ruleset 尚未建立；建立前不得覆盖或删除正式 tag，发版修复需使用新版本号。

这些属于 GitHub 仓库策略，不能只靠仓库内 YAML 代替；main 保护已启用，需归档保护 API 响应；`v*` tag ruleset 未建立，完成后再归档其规则记录。

## 12.4 支持版本与依赖维护

- Node 使用 24 LTS；Rust 工具链固定为 `1.95.0`。升级工具链单独开 PR，并在 Ubuntu/Windows 全量验证。
- Dependabot 每周检查 npm/Cargo、每月检查 GitHub Actions；生产依赖漏洞不得静默忽略。
- 每个季度至少完成一次依赖与工具链升级；高危漏洞进入最近 patch，不等待季度窗口。
- 发布前保存 `Cargo.lock`、`pnpm-lock.yaml`、CI run、安装包哈希和签名验证结果。
- 2026-10-25只读核验：[历史v0.2.0](https://github.com/kevinalliswell/TMH-LPF-900/releases/tag/v0.2.0)已发布，资产包含Windows原生EXE、macOS DMG/tar.gz、updater签名与latest.json，但尚无本轮source SBOM/全资产manifest。这是既有历史状态，不能追记成通过了新门禁；本任务不修改该发布。

## 12.5 路线与退出条件

| 版本 | 目标 | 必须满足的退出条件 |
|---|---|---|
| `v0.2.x` | 安全控制面与壳加固 | MFC 写事务有设备确认；所有退出路径不虚报安全完成；CSP/最小 capability；依赖审计；发版门禁生效 |
| `v0.3.x` | 真机传输与配置闭环 | real/replay 不再使用 MockTransport；无效现场配置 fail closed；串口探针、断线重连和故障注入验收完成 |
| `v0.4.x` | 操作员/管理员边界与数据质量 | 启动新鲜度门禁；GB 分析输入和实验类型校验；删除需管理员认证；稳定错误码覆盖前后端 |
| `v1.0.0` | 现场合格版本 | Windows 离线安装与 Authenticode；真实 MFC/温度/天平全链路；断电恢复；更新演练；实验室签字验收与回滚包 |

未满足某一行退出条件时，可以继续发该阶段的 prerelease（例如 `v0.3.0-rc.1`），不得提升到下一正式阶段。

## 12.6 回滚与支持

- 每次正式发布保留上一正式版离线安装包、数据库备份说明和配置 schema；升级前先导出配置与数据库。
- 数据库/schema 变更必须具备前向迁移测试；不能安全降级时，在发布说明中明确“程序可回滚、数据不可回滚”。
- 现场故障先执行保护气氛和停机 SOP，再收集版本、审计日志、设备配置摘要和故障时间；禁止用开发版覆盖现场证据。


## 12.7 门禁回归与验证日志

`pnpm test:scripts` 独立运行Node内置测试：IPC键名/注册/错误返回、SemVer/版本/CHANGELOG、临时仓库tag来源、预发布版本同步及标记丢失。前端Vitest只收集src测试，避免混用两套runner。CI与candidate归档测试日志和`verification/context.json`，包含实际测试SHA/父提交/工具链/平台；失败也上传已有日志，默认保留30天。main保护实况、当前issue和外部验收缺口见[推进与验收索引](26-Issue推进与验收索引.md)。

## 12.8 Rust 依赖安全门

`rust-audit.yml` 使用固定的 `cargo-audit 0.22.2`（安装使用 `--locked --no-default-features`）扫描提交中的完整 `Cargo.lock`，不按本机平台过滤。它重新取得 [RustSec 官方数据库](https://rustsec.org/) 并记录Git SHA；获取/解析失败、扫描stderr诊断、未接受的漏洞或 `unsound` 公告均使检查失败。未维护和撤包警告保留在报告中供升级评估。原报告不忽略公告；当前仅有精确glib 0.18.5临时例外，到期2026-11-20，风险与复查依据见[安全基线](27-Rust依赖安全基线.md)。

普通CI调用该门；candidate审计与安装包构建使用相同的PR head SHA，成功后才进入构建；正式release也必须先通过审计。合入main后每周二00:30 UTC重新扫描默认分支，另支持手动运行。缓存仅保存固定版本工具，数据库仍每次更新。扫描不会自动修改锁文件或升级依赖。

每次归档 `rust-audit-<run>-<attempt>`：源码SHA、Cargo.lock SHA256、工具版本、数据库SHA、原始JSON报告、独立stderr日志及策略决定，失败也保留，默认30天。JSON与stderr分离，不能将“下载失败/没有报告”解释为无漏洞。正式发版需另行长期保存该证据。后续Cargo检查和打包均使用`--locked`，避免审计后自动换用其他依赖。

本机复现：先安装同版本工具，取得官方数据库的最新Git检出并`cargo fetch --locked`，再运行 `pnpm audit:rust <数据库路径>`。修复优先升级可兼容的依赖；例外必须精确公告/包/版本并记录受影响路径、原因、责任人和不超过30天期限，脚本验证到期，不自动续期。不能以 `continue-on-error` 或关闭安全门绕过。建议required checks增加CI中的 `RustSec CI / audit`，实际启用状态仍以仓库保护API为准。candidate/release使用不同调用名，避免跨工作流同名检查混淆。

## 12.9 SBOM与资产清单

candidate和正式草稿使用固定工具生成与构建SHA绑定的源码锁文件SBOM。打包时验证真实工作区干净与SBOM来源一致；manifest逐项记录资产摘要，SHA256SUMS同时覆盖manifest。正式草稿在两个平台构建完成后核对latest.json、签名文件和实际资产，再附CHANGELOG、部署/治理及验收索引，详见[交付规则](28-SBOM与交付资产校验.md)。该阶段不自动发布草稿；签名信任、匿名分发、现场升级/回滚仍需实际证据。
