## 顺序与验收

1. **命令错误契约（#21 / #82 / #83）**：所有可失败命令返回 `code/message_zh/detail`；前端统一读取，保留框架传参错误。权限、删除、分析类型和无效输入有 IPC 断言，拒绝不写 DB。
2. **启动与运行模式边界（#19 / #79）**：严格解析模式，启动失败可在 UI 复核；requested/effective 一致。厂家协议未核实前 real 不得启用；replay 必须显式会话，不能生成模拟回执。
3. **持续验证与交付治理（#23 / #45 / #48 / #49 / #82 / #85 / #88 / #89）**：强化 IPC、发布输入和 CI 证据门禁；文档建立每条 issue 的实现、测试及外部前置索引。
4. **后续软件批次（#21/#41/#45/#83/#85/#23/#89）**：逐命令授权/拒绝审计、Rust依赖安全门、SBOM与正式资产checksum；各自独立PR并全量验证。
5. **现场门（#80 / #81 / #86 / #87）**：固定设备型号/手册、串口抓包、现场 Windows、同批样品及允许差异阈值到位后执行。缺少证据时保持未验收；不把模拟 soak 等同真机实验。
6. **扩展池（#90）**：按该 issue 的进入条件，在 v1.0 现场通过、场景与负责人确定前不进入开发。

每批提交前：fmt、clippy、工作区 Rust（普通与 candidate）、前端 typecheck/lint/test/build、IPC/安全/版本门禁、serial 编译、dirty replay 与 mock soak、生产依赖审计。PR 的 Linux/Windows CI 和 Windows/macOS candidate 结果另行核对。
